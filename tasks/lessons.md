### 회귀 fix 는 입력 규모가 외부 상황(약세장/강세장)에 따라 변하면 양쪽 극단에서 검증

**Context:** 스캐너 빈 화면 회귀를 06-08 에 `sort_tp=3→1` 로 고치고 약세장(ka10027 상승종목 ~350)에서 top_movers 100 정상 확인 → "정상화" 판정. 06-09 강세장(상승종목 ~3000)에서 또 빈 화면. 진짜 원인은 `index.ts` 의 `stocks.in("code", codes)` 대량 조회가 codes 폭증 시 PostgREST URL 한계(414)로 통째 실패 → `eligibleCodes` 빈 Set → `rebuildTopMovers` 화이트리스트 필터에서 전부 탈락 → top_movers 0.

**Mistake:**
1. `.in()` 대량 조회 실패를 첫날 의심했으나 sort_tp 문제(양수 0개)에 가려 데이터로 안 보이자 "틀린 가설"로 폐기. 실제로는 **두 버그가 겹쳐** 있었고, 약세장(codes 350)에선 `.in()` 이 우연히 통과해 안 드러난 것뿐.
2. 한 시장 상황(약세장)에서만 검증하고 완료 판정.

**Rule:**
- 데이터 파이프라인 fix 는 입력 규모가 외부 상황(시장 약세/강세)에 따라 10배 변동하면 **양쪽 극단을 가정해 검증**. 한 시나리오 통과 = 다른 시나리오 OK 아님.
- 한 근본 원인을 확정해도 초기 가설을 폐기할 땐 "이 시나리오에서만 안 보이는 것 아닌가" 자문. 데이터로 **반증** 못 하면 "틀림"이 아니라 "보류".
- `supabase-js` `.in(col, arr)` 대량 조회는 청크 분할 필수 (PostgREST URL ~414 한계). 입력이 수천 개 가능한 경로는 500개씩 청크 + `error` 처리.

**Preventive check (DB 조회가 가변 규모 입력을 받을 때):**
- `.in()`/`IN (...)` 입력 배열이 수백+ 가능하면 청크 분할 (기본 500)
- 조회 결과를 필터/조인에 쓰는데 `error` 를 무시하면 실패 시 빈 결과가 silent 하게 잘못된 출력 생성 → `error` 반드시 throw 또는 로깅 (`const { data } = await ...` 처럼 error 누락 금지)

### Turbopack dev 는 `.js`→`.ts` re-export resolve 못함 — 첫 런타임 값 re-export 도입 시 회귀

**Context:** Phase 10-08 배포 검증 중 `/themes`·`/stocks/[code]` 가 DEV 에서만 Build Error 오버레이. 원인은 10-02 가 `packages/shared/src/index.ts` 에 추가한 첫 **런타임 값** re-export (`export { THEME_STOCK_SOURCES } from "./theme.js"`). webapp tsconfig `paths` 가 `@gh-radar/shared` 를 src(`.ts`)로 라우팅하는데, Turbopack dev 는 webpack 의 `extensionAlias` 같은 `.js`→`.ts` 자동 매핑이 없어 명시 `.js` re-export 를 못 푼다. `type` re-export 는 컴파일 타임 소거라 안 터졌고, production `pnpm -F webapp build`(webpack)는 항상 green — **DEV 전용** 회귀라 build 게이트로 못 잡음.

**Mistake:** `.js` 확장자 명시가 NodeNext 관용이라 무비판 적용. 같은 배럴을 Turbopack(bundler resolution)이 소비한다는 점 + "type 만 re-export 하다가 처음으로 값 re-export 추가" 가 트리거라는 점을 사전에 못 봄.

**Rule:**
- webapp(Next/Turbopack)이 소비하는 공유 배럴(`packages/shared/src/index.ts`)의 re-export 는 **확장자 없이** 쓴다 (`from "./theme"`). `moduleResolution:bundler` 관용이고, NodeNext 소비자(server/worker)는 빌드된 `dist` 를 쓰므로 무영향.
- 공유 패키지에 **첫 런타임 값**(상수/함수) re-export 를 추가할 때는 `pnpm -F webapp dev` 로 실제 페이지를 한 번 열어 확인. production build green ≠ dev green.

**Preventive check (공유 배럴 수정 시):**
- `git diff packages/shared/src/index.ts` 에 `export {` (값) 신규 추가가 있으면 dev 스모크 필수
- 배럴 re-export 는 확장자 생략 통일 (`grep '\.js"' packages/shared/src/index.ts` 가 비어야 함)

### 인계 컨텍스트의 "PASS/FAIL 상태"는 그대로 믿지 말고 실측으로 재확인

**Context:** Phase 10-08 finalize 인계 노트가 "edit/delete/fork user-themes E2E 는 이미 PASS(6/7 green)", "stock-detail-chart.spec 도 unmocked 데이터로 실패" 라고 명시. 실측하니 (a) edit-remove/delete/fork 는 **pre-change baseline 에서도 실패**(Express `/api/themes/:id` 부재로 상세 에러 카드 — 노트와 반대), (b) `stock-detail-chart.spec` 는 **4/4 green**(노트와 반대), 실제 미해결은 `stock-detail.spec.ts:15` 단일 stale assertion 뿐.

**Mistake (잠재):** 노트의 "6/7 green" 을 믿고 edit-remove 실패를 내 optimistic 변경 탓으로 오귀인하거나, chart spec 을 deferred 로 잘못 기록할 뻔.

**Rule:**
- 인계받은 "X 는 통과/실패" 주장은 fix/finalize 전에 **해당 테스트만 직접 실행**해 1차 사실 확인. 특히 "내 변경이 깬 것 같다" 판단 전에 `git stash` 로 pre-change baseline 에서 같은 테스트를 돌려 **회귀 여부를 분리**한다.
- deferred/out-of-scope 로 문서화할 항목도 실제 실패 메시지를 한 번은 캡처(추정 금지) — 후속 작업자가 정확한 원인을 받게.

**Preventive check (finalize/회귀 의심 시):**
- 의심 테스트 단건 실행 → 실패 시 `git stash push -- <changed files>` 후 재실행 → pop. baseline 에서도 실패면 pre-existing(내 탓 아님), baseline 통과면 내 회귀.
- deferred 기록은 파일:라인 + 실제 assertion + 진짜 원인(추정/실측 구분) 명시.

## 프론트↔서버 응답 계약 드리프트 — 양쪽 테스트가 각자 다른 계약을 박제 (Phase 10, 2026-06-10)

**Context:** 테마 상세 클릭 시 전역 `error.tsx`("문제가 발생했어요"). 서버 `GET /api/themes/:id` 가 bare `ThemeStockMember[]` **배열** 을 반환했는데, webapp `fetchSystemThemeDetail` 은 `ThemeWithStats & { stocks }` **객체** 를 기대(`apiFetch<T>` 로 단언). 응답이 배열이라 `theme.sources` 가 undefined → `ThemeSourceBadges` 의 `sources.filter()` 가 렌더 중 throw → 전역 경계. (상세 페이지는 메타를 prop 으로 안 받고 URL 직접 진입 가능 → 서버가 메타까지 반환해야 함.)

**Mistake (systemic):** 서버 테스트는 `expect(Array.isArray(r.body)).toBe(true)` (배열)를, webapp 컴포넌트 테스트는 `fetchSystemThemeDetail` 을 `detail({...})` **객체** 로 mock — **양쪽 다 green 인데 실제 wiring 은 깨짐**. 각 테스트가 자기편 계약만 박제하고, 둘을 묶는 검증이 없어 드리프트가 prod 까지 샘. webapp 의 mock 은 "서버가 실제로 그렇게 응답한다" 는 증거가 아니다.

**Rule:**
- 프론트 fetch 래퍼가 응답 타입(`apiFetch<T>`)을 선언하면, 서버 라우트의 `res.json(...)` 인자를 **같은 shared 타입 `T` 로 타이핑** 하거나(이상적으로 packages/shared 의 응답 타입 공유), 최소한 양측이 합의하는 **계약 테스트 1개** 를 둔다. 한 쪽 mock/assertion 을 계약 증명으로 믿지 말 것.
- `res.json(array)` vs 래퍼의 객체 기대처럼 **shape(배열↔객체) 불일치** 를 특히 경계 — TS 는 패키지 경계를 넘는 런타임 응답을 검사하지 못한다.

**Preventive check:**
- `error.tsx`("문제가 발생했어요")는 fetch 실패가 아니라 **렌더 중 throw** 신호 (fetch 실패는 보통 컴포넌트 자체 try/catch → 에러 카드). 데이터 **모양 불일치**(undefined 필드의 `.map`/`.filter`)를 먼저 의심.
- 새/변경 API 는 배포 후 prod `curl` 로 **응답 형태**(배열 vs 객체 + 필수 필드 존재)를 직접 확인. 프론트가 `apiFetch<T>` 로 단언하는 모든 엔드포인트는 서버 `res.json` 인자 타입이 `T` 와 일치하는지 점검.

## `.in()` 입력 청크 ≠ 결과-행 보호 — db-max-rows(1000) 페이지네이션 별도 필요 (Phase 10, 2026-06-10)

**Context:** `/api/themes` 목록의 테마 66%(235/356)가 stockCount=0 으로 표시. 데이터는 정상(워커가 7544 active 링크 적재, "2차전지" 실제 144종목, 상세 라우트는 정상). 원인은 목록 라우트 `fetchActiveThemeStocksChunked` 가 theme_id 를 200 씩 `.in()` 청크하지만, **한 청크가 매칭하는 theme_stocks 결과 행이 PostgREST db-max-rows(기본 1000)에서 통째로 잘려** 1000행 너머 테마가 사라진 것. **스모킹건: 목록 stockCount 합계가 정확히 2000(=2 청크 × 1000).** 상세(`/:id`)는 단일 테마(≤144행)라 한계 미도달 → "0종목인데 누르면 종목이 나오는" 비대칭.

**Mistake:** 커밋 37afcde 가 `.in()` 을 청크한 건 **URL 길이(414)** 대비였는데, 그게 **결과-행 한계(db-max-rows)** 까지 막아준다고 착각. 둘은 다른 축이다 — 입력 code/id 를 N 개로 나눠도, 한 청크가 반환하는 **행 수**가 1000 을 넘으면 응답이 잘린다. 게다가 테스트 mock(`supabase-mock`)이 db-max-rows 를 미시뮬레이션(모든 행 반환)이라 회귀가 또 prod 까지 샘([[프론트↔서버 계약 드리프트]] 와 동일한 "mock 이 실서버 제약을 안 닮음" 메타-실수).

**Rule:**
- `supabase.from(t).in(...)` / `.eq(...)` 가 **여러 부모에 걸쳐 수백~수천 행을 반환**할 수 있으면, 입력 청크와 **별개로** 결과 행을 `.range(from, from+PAGE-1)` 로 끝까지 페이지네이션한다(안정 정렬 PK + advance-by-actual-rows + break-on-empty → db-max-rows 값과 무관하게 정확). 단건/소수 부모(`.eq(id)`) 조회는 행 수가 작아 불필요.
- 한계 가늠법: **응답 행 합계가 딱 떨어지는 1000 배수**면 db-max-rows 절단을 의심.

**Preventive check:**
- DB mock 은 실서버 제약(여기선 db-max-rows 1000)을 **시뮬레이션**해야 회귀를 잡는다. `supabase-mock` 에 `.range()` + 1000행 캡 추가 완료 → active>1000 회귀 테스트가 페이지네이션 누락 시 fail.
- 가변 규모 `.in()`/`.eq()` 조회를 추가/수정할 때: (1) 입력 URL 청크 했는가(414), (2) 결과 행 페이지네이션 했는가(db-max-rows) — **둘 다** 점검.

## 정량 주장은 단언 전에 실측 — subagent 의 "대부분/majority" 를 수치로 인용 금지 (Co-movement 디스커션, 2026-06-10)

**Context:** 상한가 동조 종목 phase 아이디어 디스커션에서, 테마없는 종목 비율을 Explore subagent 의 정성 표현("majority of ~2,800 stocks are theme-less")을 그대로 받아 사용자에게 "**테마없는 종목 ~40%**, 섹터도 NULL이라 fallback 없음" 으로 단언. 사용자가 "섹터가 없는 대신 테마가 있어. 체크해봐" 로 교정. read-only 실측 결과 **활성 2,778 중 2,476(89%) 테마 보유 — 미분류 11%**, 급등 앵커도 89%·고이벤트 92% 테마 보유. "40%"는 ~4배 과대였고, 그에 기반한 "테마없는 종목 보완책" 우려 자체가 거의 무의미했음.

**Mistake:** 같은 세션에서 급등 **이벤트 희소성은 실측**(probe script)했으면서 **테마 커버리지는 subagent 추정으로** 빠진 비대칭. subagent(Explore)는 "코드/문서를 훑은 인상"을 줄 뿐 집계(COUNT/DISTINCT)를 하지 않는다 — "majority/most/대부분"은 측정값이 아니라 어림짐작인데 이를 `%` 수치로 승격해 인용.

**Rule:**
- 설계 결정을 좌우하는 **정량 주장(커버리지 %, 분포, 빈도, 비율)**은 DB/실데이터 접근이 가능하면 **사용자에게 말하기 전에 직접 measure**. 이 프로젝트는 `workers/master-sync/.env`(SUPABASE_URL+SERVICE_ROLE_KEY)로 read-only 집계 가능 — `NODE_PATH=workers/master-sync/node_modules node probe.cjs` 패턴.
- subagent 의 "대부분/majority/most/~ 추정" 류 표현을 **수치(%) 로 변환해 단언 금지.** 출처를 (a) 직접 쿼리 (b) subagent 인상 (c) 내 추측 으로 구분하고, (b)(c)이면서 접근 가능하면 (a)로 승격.
- 한 축(이벤트)만 재고 다른 축(테마 커버리지)을 추정으로 남기는 **비대칭 검증** 경계 — 같은 결정에 쓰이는 정량 입력은 같은 엄밀도로.

**Preventive check (사용자 대면 정량 주장 직전):**
- 문장에 `N%` / "대부분" / "다수" / "거의 없음" 이 있으면: 이 숫자 직접 쟀나? 못 쟀고 DB 접근 가능하면 probe 먼저.
- gh-radar read-only probe: `dotenv` → `createClient(SUPABASE_URL, SERVICE_ROLE_KEY)` → `.select('*',{count:'exact',head:true})`(집계) / `.range()` 페이지네이션(분포). 집계 숫자만 출력, 시크릿 미출력.

## 커밋 승인은 "보여준 범위 = 스테이징 범위" — scoped `git status` 후 `git add -A` 금지 (Phase 11 디스커션, 2026-06-10)

**Context:** discuss-phase 산출물 커밋 시 변경 목록을 `git status --short -- .planning tasks` 로 **pathspec 좁혀** 확인 → 그 5개만 대상으로 한 commit 메시지를 사용자에게 제시 → 승인("응") → 그런데 실제론 `git add -A` 로 스테이징해서, 사용자 working tree에 있던 **무관한 WIP**(theme-admin overrides: server/webapp/workers 코드 + 새 migration + hook 등 11파일)까지 `docs(11)` 메시지로 함께 커밋. push 전에 발견·정정(soft reset → 명시 경로만 재스테이징 → 재커밋 → push).

**Mistake:** (1) 커밋 미리보기 `git status` 를 `-- .planning tasks` 로 좁혀 tree의 다른 변경을 **사용자에게 안 보여줌**. (2) 보여준 범위는 좁은데 스테이징은 `git add -A`(전체) — **보여준 범위 ≠ 스테이징 범위**. 결과적으로 승인받은 것과 다른 커밋 + 검증 안 된 남의 WIP를 잘못된 메시지로 묶음.

**Rule:**
- 커밋 승인을 받을 땐 **pathspec 없는 전체** `git status --short` 로 working tree 전부를 보여준다. 일부만 커밋할 거면 "나머지 X는 제외/보존" 을 명시.
- 스테이징은 **보여준 그 경로만 명시적으로** `git add <paths>`. scoped 미리보기 뒤 `git add -A`/`git add .` 금지 — 보여준 범위와 스테이징 범위가 어긋난다.
- 사용자 tree에 **무관한 WIP가 있을 수 있다고 항상 가정.** 내가 안 만들었거나 빌드/테스트 검증 못 한 변경을 내 docs/feature 커밋에 묶지 않는다. (`한번에 커밋` 규칙이 있어도 — 그 규칙은 "tree 전체를 보여주고 정확히 기술" 을 전제로 한다.)

**Preventive check (커밋 직전):**
- `git status --short` (pathspec 없이) 출력 == 내가 제시한 파일 목록인가?
- `git diff --cached --name-only` 로 스테이징된 게 제시 목록과 동일한지 commit 전 확인.
- 무관 WIP 발견 시: push 전이면 `reset --mixed HEAD~1` → 명시 경로만 재스테이징.

## 외부 API 의 stale 응답은 "0행 가드"로 못 잡는다 (quick 260720-kbf, 2026-07-20)

**Context:** intraday-sync 는 휴장일 가드로 "ka10027 응답 0행"만 검사했다. 그런데 키움 ka10027 은 휴장일/프리마켓에 **직전 거래일 snapshot 을 0행이 아니라 통째로 그대로 반환**한다. 그 결과 0행 가드를 통과해, 전날 등락률(예: +30%)을 담은 행이 오늘 날짜로 `stock_daily_ohlcv` 에 INSERT → 044380 종목상세에 가짜 '상'(상한가) 마커가 표시됐다. 실제로 05-25(석가탄신일 대체)·06-03(지방선거일)·07-17 세 날짜가 오염됐고, 각 날짜 행의 84~89% 가 직전 거래일과 close/change_rate 완전 일치(= stale 증거)였다. 휴장일이라 candle-sync(공식 KRX EOD) 는 해당 날짜 데이터를 쓰지 않아 stale intraday 행이 덮이지 않고 잔존.

**Mistake:** "데이터가 없으면 0행" 이라는 가정으로 휴장 판정을 응답 개수에만 의존. 외부 API 가 캐시/직전값을 재방출하는 실패 모드를 고려하지 않음.

**Rule:** 외부 시세 API 로부터 받은 배치를 저장하기 전에 **내용 기반 stale 감지**를 둔다. 저장된 직전 거래일 값(close, change_rate)과 이번 배치를 비교해, 비교 가능 표본이 충분(예: ≥30)하고 일치율이 높으면(예: ≥0.8) "직전값 재방출"로 판정하고 cycle 을 skip 한다. "응답이 비었나?" 뿐 아니라 "응답이 어제와 똑같나?" 를 항상 함께 검사. 표본 부족 시엔 오탐 방지를 위해 판정 보류(통과)하되, 비교용 조회는 error 를 삼키지 말고 fail-fast(빈 결과로 가드가 무력화되는 것 방지).

## UI/IA 결정은 "결정 순서 → 한 번에 하나 → 요청한 목업만" (Phase 15 UI-phase, 2026-09-05)

**Context:** 호가창 마운트 위치를 정하면서 안 1/2/3 을 ASCII 프리뷰 3개 + 후속 질문 2개(진입 카드 위치·탭 컴포넌트)와 함께 한 다이얼로그에 몰아 물었고, 사용자가 "목업으로 보여줘"라 하자 요청하지 않은 4열 비교 매트릭스(실측 높이·폭 표 포함)를 만들어 다시 3질문을 던짐. 사용자: "뭐가 뭔지 하나도 모르겠어 하나씩 천천히 설명하고 목업도 만들어. 이게 뭐야 니맘대로 다 만들고" / "뭐가 문제인지 뭐부터 결정해서 결정해야 할지 제대로 판단하고 진행해". 사용자가 직접 "모바일을 생각하면 상단탭"을 제시했고 그것이 정답이었다(토스증권·네이버 금융 관례).

**Mistake:**
1. 결정 순서를 먼저 세우지 않고 옵션·근거·수치를 한꺼번에 쏟았다.
2. 요청받지 않은 산출물(비교 매트릭스)을 만들어 인지 부하를 키웠다.
3. 우리 코드의 선택값(`max-w-4xl` 896px)을 근본 제약으로 오판해 탭 안을 "레이아웃 후퇴"로 비추천했다. 컨테이너 폭은 탭별로 바꾸면 그만이었다.
4. 모바일 기준을 먼저 세우지 않았다.

**Rule:**
- IA/UI 결정 요청이 오면 먼저 **결정해야 할 것을 순서대로 2~3개로 적고** 첫 번째만 묻는다. 한 다이얼로그에 질문 1개. 다음 결정은 앞 결정이 끝난 뒤.
- 목업은 **사용자가 말한 그 안 하나**를 만든다. 비교 매트릭스·실측 표는 요청 없으면 만들지 않는다.
- 어떤 안을 "불가"로 판정하기 전에 근거가 **외부 제약인지 우리 코드의 선택값인지** 구분한다. 선택값이면 바꾸는 비용만 적고 불가 판정을 내리지 않는다.
- 종목상세·트레이딩 표면은 **모바일 390px 부터** 설계하고 데스크톱은 그다음. 종목상세는 상단 4탭(차트·호가주문·종목정보·뉴스토론)으로 확정(CONTEXT 15 D-02a).

## 손보는 표면 안의 시각 결함은 "보고 후 대기" 말고 그냥 고친다 (Phase 15 호가창 디자인, 2026-09-06)

**Context:** 호가주문창 재배치 작업 중, 체결 테이프가 `table-fixed` 4등분(220px 컬럼 → 열당 39px)이라 체결가 `98,100` 이 `98,1`/`00` 두 줄로 쪼개지는 것을 스크린샷으로 확인했다. 내 변경이 만든 회귀는 아니고(폭은 그대로) 사용자가 지목한 3개 항목에도 없어서, "기존 문제지만 이제 맨 왼쪽 열이라 더 눈에 띈다, 원하시면 손보겠다"고 **보고만 하고 멈췄다**. 사용자: "a 줄바꿈 안되게 손보고 커밋 및 배포하자" — 결국 한 턴을 왕복으로 버렸다.

**Mistake:** "요청 범위 밖"과 "요청한 표면 안의 명백한 결함"을 같은 저울에 올렸다. 사용자가 "디자인을 좀 손볼거야"라며 연 표면에서, 한 줄짜리 수정으로 없어지는 가독성 결함을 결정 사항으로 승격시켰다.

**Rule:** 사용자가 손보라고 연 화면 안에서 발견한 시각 결함이 (a) 수정이 국소적이고 (b) 판단이 갈릴 여지가 없으면(줄바꿈·잘림·겹침·정렬 깨짐 등 명백한 것) **그냥 고치고 결과에 한 줄로 밝힌다.** 왕복해서 물을 것은 취향이 갈리는 것(색·간격·정보 위계 변경)이나 다른 표면까지 번지는 것뿐이다. 반대로, 요청한 표면 **밖**의 결함은 지금처럼 보고만 한다.

**보너스(같은 작업에서 통한 것):** 폭 계산은 손으로 추정하지 말고 Playwright 로 `scrollWidth > clientWidth` + 행 높이를 실측해 두 번 만에 수렴시켰다. 픽셀 배분은 계측이 추정보다 싸다.

## 그리드/플렉스 자식은 `min-w-0` 없으면 조용히 **잘린다** (Phase 15 호가창, 2026-09-07)

**Context:** 사용자가 아이폰 스크린샷으로 "호가주문창이 잘려보여"를 제보. 픽스처 데이터(잔량 10~100)로는 320~390px 어느 폭에서도 재현되지 않았다. `document.scrollWidth - clientWidth == 0` 이라 "가로 넘침 없음"으로 오판하기 쉬웠는데, 섹션이 `overflow-hidden` 이라 **넘친 만큼이 스크롤이 아니라 잘림으로 나타나** 문서 레벨 계측에 안 잡혔다. 그리드 자식에 줄바꿈 불가 문자열 1줄을 주입하는 실험으로 사다리 폭이 324 → 333px 로 밀려나는 것을 확인해 원인을 특정했다.

**Mistake:** ① 재현이 안 되자 "브라우저 엔진 차이"·"핀치 줌" 같은 환경 가설로 새려 했다. ② `documentElement.scrollWidth` 만 보고 넘침이 없다고 결론 낼 뻔했다 — 조상에 `overflow-hidden` 이 있으면 그 지표는 항상 0이다.

**Rule:**
- CSS Grid/Flex 자식의 기본값은 `min-width: auto` 라 **콘텐츠 최소폭 아래로 줄지 않는다.** 반응형 컨테이너 안의 그리드/플렉스 자식에는 `min-w-0` 을 기본으로 건다. 특히 표·`<select>`·긴 문자열을 품은 자식.
- `display: contents` 래퍼의 **자식**이 진짜 그리드 아이템이다. 래퍼에만 `min-w-0` 을 걸면 좁은 폭에서 무효 — 자식에 직접 걸어야 한다.
- 잘림 진단은 문서 스크롤폭이 아니라 **의심 요소의 실측 폭이 컨테이너를 넘는가**로 한다. 재현 데이터가 없으면 "긴 unbreakable 문자열을 자식마다 하나씩 주입하고 형제 폭이 밀리는지" 보는 격리 실험이 빠르다. 그리고 그 실험을 그대로 수용 기준(회귀 테스트)으로 남긴다.
- 표는 `table-fixed` 여도 안전하지 않다 — 표 자신은 안 넘쳐도 **형제 그리드 아이템**이 열을 밀면 같이 잘린다.

**부수 교훈:** `text-center` 셀 오른쪽에 조건부 배지(`체결`)를 붙이면 그 행만 가운데축이 밀려 **틱마다 좌우로 흔들린다.** 실시간 갱신 표에서 현재가 표시는 레이아웃 폭을 차지하지 않는 방식(배경·테두리·absolute)만 쓴다.

## "필터를 풀면 뒤에서 무엇이 흘러 들어오는가"를 먼저 세어라 (quick-260908-fis, 2026-09-08)

**Context:** 채비(`0011T0`)가 스캐너에 안 보인다는 제보. 원인은 intraday-sync 매퍼의 `/^\d{6}$/` — KRX 가 2025년부터 발급하는 영문 포함 단축코드를 전부 버리고 있었다(무로그 catch 라 프로덕션 로그엔 `mapErrors: 347` 이라는 숫자만 남았다). 정규식을 `^[0-9A-Z]{6}$` 로 넓혀 배포하자 채비는 즉시 rank 15 로 진입했지만, **같은 문에서 영문코드 ETF 297종이 함께 들어와** SK하이닉스 단일종목 레버리지 ETF 7종·원자력 ETF 3종이 급등 목록에 올라갔다.

**Mistake:** ① 진단 단계에서 "마스터의 영문코드 종목 80개" 만 세고, **ka10027 응답 쪽에 몇 개가 있는지는 세지 않았다.** 실제 유입은 297개였고 대부분이 ETP였다. 차단기를 풀 때 세어야 할 것은 *통과시키고 싶은 것*이 아니라 *통과하게 될 전부*다. ② `fetchEtpBaseInfo.ts` 의 숫자 전용 필터를 **주석만 읽고 "의도된 동작"으로 스코프에서 뺐다.** 그 주석("키움은 6자리 숫자만 반환하므로 영문코드 ETP 는 매칭 불가")의 전제는 *우리 매퍼가 버려서 그렇게 보였던 것*이었다 — 같은 버그가 만든 착시를 그 버그를 안 고칠 근거로 인용한 셈이다.

**Rule:**
- **필터 완화 = 신규 유입.** 정규식·화이트리스트·임계값을 넓히기 전에 "완화 후 통과할 전체 집합"을 데이터로 세고, 그 집합이 **하류의 분류·집계에서 어떻게 취급되는지**를 한 단계씩 따라간다. 여기선 `map.ts` → `bootstrapMissingStocks`(모르는 코드에 `security_group='주권'` 부여) → `rebuildTopMovers` 화이트리스트 통과가 한 줄로 이어져 있었다.
- **모르는 것에 기본값으로 신원을 부여하지 말 것.** bootstrap 의 목적은 FK orphan 회피이지 분류가 아니다. `'주권'` 대신 어느 화이트리스트에도 없는 sentinel(`'미확인'`)을 넣으면, 마스터가 정확한 값으로 덮을 때까지 자동으로 배제 상태가 유지된다. "기본값이 곧 통과"인 구조를 만들지 않는다.
- **코드 주석의 전제는 근거가 아니다.** 특히 "다른 시스템이 X만 준다"류의 외부 전제는 그 주석을 쓴 시점의 관측이며, 지금 고치고 있는 버그가 만들어낸 관측일 수 있다. 스코프 제외를 주석에 근거해 결정할 거면 그 전제를 실데이터로 한 번 확인한다.
- **블랙리스트(`NOT IN ('ETF','ETN','ELW')`)와 화이트리스트가 공존하면 신규 값에서 갈린다.** 이번 sentinel 은 top_movers 화이트리스트에선 배제되지만 comovement/cosurge 의 블랙리스트는 통과한다. 새 분류값을 도입할 때 두 방식 모두 점검할 것.

## 목업 시각 확인 게이트를 건너뛰고 UI-SPEC 을 확정·커밋하지 말 것 (ui-phase 16, 2026-09-08)

**Context:** `/gsd-ui-phase 16`. researcher 가 목업 3건을 만들어 `open` 했고, 나는 `--warn` 토큰 질문 1개만 물은 뒤 checker 검증 → 수정 루프 → 커밋 → push 까지 한 번에 끝냈다. 사용자는 목업을 아직 검토하지 않은 상태였다.

**Mistake:** ① 프로젝트 규칙(목업 → **사용자 시각 확인** → 채택 → UI-SPEC)의 "사용자 확인" 단계를 "브라우저로 열어 둠" 으로 대체했다. 열어 둔 것과 검토받은 것은 다르다. ② 전역 규칙 "커밋 전 메시지 보여주고 확인" 을 GSD `commit_docs: true` 가 대신한다고 해석했다. 워크플로우 설정은 *커밋해도 되는 종류*를 정하는 것이지 사용자 승인 게이트를 없애는 게 아니다. ③ "자율 모드" 지시를 "사용자 검토 없이 마무리" 로 읽었다. 자율은 *가역적이고 요청에서 따라 나오는* 작업에 한정이며, 디자인 채택은 사용자 판단이 곧 산출물의 내용이다.

**Rule:**
- **UI 목업은 사용자가 보고 답하기 전까지 초안이다.** 목업을 연 뒤에는 반드시 멈추고 AskUserQuestion(변형 채택/수정 요청/승인)으로 검토 결과를 받는다. checker·UI-SPEC 확정·커밋은 그 답 이후에만 진행한다.
- **`commit_docs: true` 는 커밋 허가가 아니라 커밋 대상 정의다.** 이 프로젝트에서 커밋은 항상 메시지를 먼저 보여주고 확인받는다. push 도 같은 확인에 포함.
- **"열어 두었다" 를 보고에 쓰지 말 것.** 사용자가 아직 보지 않은 것을 완료처럼 서술하지 않는다.

## 선택지는 「언제」가 아니라 「무엇을 건드리는가」로 갈라서 제시하라 (quick-260916-c9y, 2026-09-16)

**Context:** radar-gw 에 측정기를 넣는 작업에서 VM 반영 방식을 A/B/C 로 물었다. 나는 옵션을 "지금 / 장 마감 후 / 지금 전체 재적용" 이라는 **시점**으로만 갈라 놓았다. 사용자는 고르지 않고 "무슨 차이인지 설명을 좀 더 해줘" 로 되물었다.

**Mistake:** 옵션이 실제로 갈리는 **원인 메커니즘**을 말하지 않았다. 이 저장소는 `setup-relay-iam.sh` → 메타데이터 → `google_metadata_script_runner` 라는 경로가 하나뿐이고 **부분 적용이 없어서**, "자산 하나 추가" 가 곧 "startup.sh 665줄 전체 재실행" 이 된다. 그래서 진짜 차이는 시점이 아니라 **건드리는 범위**(신규 유닛 1개 vs apt 8종·docker 재시작·Caddyfile 재배치·route-guard 발화)였다. 그 한 줄이 없으니 옵션들이 취향 문제로 보였다.

**Rule:**
- 선택지를 낼 때 **옵션이 갈리는 기저 메커니즘을 한 줄로 먼저** 말한다. "A는 지금, B는 나중" 이 아니라 "이 경로는 부분 적용이 없어서 A는 X만, B·C는 전부를 건드린다".
- 각 옵션에 **그것이 실제로 건드리는 것의 목록**을 근거(파일·섹션 번호)와 함께 붙인다. 위험을 추상적으로 말하지 말고 "3절이 docker 를 재시작하면 relay 컨테이너가 끊긴다" 처럼 경로를 적는다.
- 한 옵션이 다른 것의 **상위집합이면 그 관계를 명시**한다("A = B + 앞에 임시 설치 한 번"). 그러면 선택이 하나의 질문으로 줄어든다.
- 고를 이유가 없는 옵션은 **왜 없는지까지 적는다**("C는 얻는 게 A와 같은데 부작용만 더 진다").

## 선행 독서량이 큰 태스크를 executor 서브에이전트에 통째로 맡기지 말 것 (quick-260916-c9y, 2026-09-16)

**Context:** `/gsd-quick` 의 `gsd-executor` 에 3개 태스크(코드 작성 + 배치 + VM 설치)를 한 번에 넘겼다. 에이전트는 `README.md` 994줄 · `startup.sh` 665줄 · `setup-relay-iam.sh` 401줄을 다 읽고 **첫 산출물을 쓰기 전에** 핸드백 강제로 잘렸다. 반환값은 **작업 0건 · 커밋 0건 · 파일 0건**이었고 약 175K 토큰과 4.5분이 소모됐다.

**Mistake:** 오케스트레이터인 내가 **이미 그 파일들을 전부 읽어** 삽입 지점·앵커·자산 등록 위치를 알고 있었는데, 그것을 프롬프트에 싣지 않고 서브에이전트가 처음부터 다시 읽게 했다. "컨텍스트를 깨끗이 유지하려고 위임한다" 를 "내가 아는 것을 넘기지 않는다" 로 잘못 실행한 것이다. 위임의 목적은 **재작업을 없애는 것**이지 정보를 감추는 것이 아니다.

**Rule:**
- 서브에이전트에 넘길 때 **이미 확인한 구조 정보(줄 번호·앵커 문자열·파일 형식·실측값)를 프롬프트에 실어** 재독서를 없앤다. "읽어라" 가 아니라 "여기 있다".
- 선행 독서량이 큰 단일 태스크는 **태스크 단위로 쪼개 각각에 필요한 파일만** 주거나, 오케스트레이터가 직접 실행한다. 3태스크 × 대형 파일 3개는 한 에이전트의 예산을 넘는다.
- **같은 방식으로 재시도하지 않는다.** 한 번 잘렸으면 실패 원인(컨텍스트 소모)을 제거한 뒤 다시 던지거나 직접 한다. 그대로 되던지면 같은 자리에서 또 잘리고 비용만 두 배가 된다.
- 되돌릴 것이 있는지 먼저 확인한다. 이번엔 커밋·파일 쓰기가 0건이라 잔여물이 `.git/gsd-plan-head-before-*` 원장 하나뿐이었고, HEAD 가 그대로여서 유효했다.

## 커널에만 넣은 규칙은 재부팅에 사라진다 — 반영은 생성물 경유, 재부팅 전 파일↔커널 대조 (quick-260916-c9y, 2026-09-16)

**Context:** radar-gw 에 startup.sh 를 재적용했더니 `wg0.conf`·`wgfwd.nft` sha 가 바뀌었다. 메타데이터 차이는 wg-probe 섹션뿐이라 바뀔 이유가 없었다. 커밋별 heredoc 해시를 재구성하니 디스크 파일은 9/9·9/11 생성물인데 커널에는 9/15 doz 의 alex-mac 전용 121 규칙이 이미 있었다. doz 가 규칙을 **커널에만** 넣고 생성물·메타데이터 재적용을 안 했던 것이다. 그대로 재부팅됐다면 121 접근이 조용히 사라졌다 — startup.sh 는 이미 기동한 wg0 를 재기동하지 않기 때문이다.
