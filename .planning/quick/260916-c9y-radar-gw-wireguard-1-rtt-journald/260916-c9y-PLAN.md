## (b) 임계값 — 이번 10.5초 사건을 실제로 잡는가부터 역산했다

**임계값 표의 단일 정본은 `infra/relay/wg-probe.py` 헤더 주석이다.**
README 는 그 위치를 가리키기만 하고 표를 복사하지 않는다 (CLAUDE.md §Conventions:
「표가 둘이 되면 갈라진다」). 아래는 계획 근거이며, 코드 헤더가 정본이다.

| 판정 | 임계값 | 근거 |
|---|---|---|
| `rx_stall` (수신 정지 + 송신 진행) | rx 무변화 **≥3초** ∧ 같은 창의 tx 증가 **≥512B** | **이번 사건의 서명이다**(한 방향만 멈춤). 3초는 10.5초의 1/3.5 — 사건 시작 3초 뒤 발화하고 종료까지 여러 줄을 남긴다. 2초로 낮추지 않은 이유: 1Hz 표본은 ±1초 양자화 오차가 있어 2초 기준은 1.x초짜리 실제 공백에도 발화한다. 3초는 **온전한 표본 간격 2개** 의 침묵을 보장한다. 512B 하한은 `PersistentKeepalive` 전용 트래픽(32B/25초)을 배제한다 — 이것이 없으면 유휴 피어가 상시 발화한다 |
| `tx_stall` (송신 정지 + 수신 진행) | 위의 대칭 | 반대 방향 고장. 같은 창에서 rx 가 ≥512B 늘어야 한다 |
| `hs_stale` (핸드셰이크 노후) | 경과 **>180초** ∧ 그 피어가 최근 60초 내 1바이트라도 움직였다 | **이번 사건을 잡지 못한다는 사실을 명시한다.** WireGuard 는 데이터가 흐르면 REKEY_AFTER_TIME(120초) 안팎으로 갱신하므로 10초 공백은 경과를 150초든 180초든 넘기지 못한다. 인계가 제시한 150초는 **이 태스크의 목적에는 무효한 기준**이다. 그럼에도 남기는 이유는 「터널 완전 사망」이라는 **다른 사건**의 신호이기 때문이고, 180초는 WireGuard 의 REJECT_AFTER_TIME — 그 시점부터 세션 키가 실제로 거부된다. 「최근 활동」 조건이 없으면 keepalive 를 끈 유휴 피어가 영구 발화한다 |
| `wg_txdrop` / `wg_rxdrop` | 증가 **≥1** | `/proc/net/dev` 의 wg0 TX drop 누적 **371**(2026-09-16 실측)이 언제 늘었는지 모르는 것이 정확히 이 측정기가 푸는 문제다. 드롭 1건도 정보이고, 폭주는 아래 분당 상한이 막는다 |
| `uplink_err` | ens4 rx/tx err·drop 증가 ≥1 | 기준선 전부 0. 상승하면 VM 업링크 쪽 증거 |
| `rtt_high` | 기준점 왕복시간 **>50ms 가 2회 연속** | 실측 기준선 KT 2.054ms · LG U+ 4.364ms. 50ms 는 12~25배로, GCP 서울↔국내 ISP 경로의 정상 지터가 절대 닿지 않으면서 유의미한 경로 열화는 놓치지 않는 자리다. 2회 연속 조건이 단발 잡음을 배제한다 |
| `rtt_loss` | 무응답 **3회 연속** | `ping -O` 의 `no answer yet` 줄을 센다 |
| 생존 | **60초**마다 `alive` 한 줄 | 하루 1,440줄(≈150KB). 상시 기록(하루 17MB)과 비교해 1% 미만. **생존 줄의 부재 자체가 「수집기가 죽었다」는 귀속 사실**이 된다 |
| 폭주 상한 | 이상 줄 **분당 20줄**, 초과분은 `suppressed n=` 한 줄로 요약 | journald 를 태우지 않는다 |

**에피소드 모델.** 같은 (kind, peer) 이상이 연속되는 동안을 하나의 에피소드로 묶어
`open` → `cont`(5초마다) → `close`(지속시간 포함) 세 종류만 낸다. 10.5초 사건이면
약 3줄이 남는다 — 초당 한 줄이 아니라.

**기준점 2곳은 국내 ISP 여야 한다.** 사건 피어 엔드포인트는 국내 ISP 회선이었고,
`8.8.8.8`(1.160ms)·`1.1.1.1`(1.514ms)은 GCP 에서 사실상 피어링 내부라 국내 경로 열화를
보지 못한다. KT(`168.126.63.1`)·LG U+(`164.124.101.2`) DNS 2곳을 쓴다 — 클라이언트 IP 를
찌르지 않는다는 LOCKED-3 과 양립한다.

## (c) 검증 — 데이터패스를 건드리지 않고 증명한다

**금지:** 인위적 장애 유발(피어 차단·nft 조작·wg0 재시작·패킷 드롭 주입). 실계좌가 걸린
실 게이트웨이다.

**대신 세 겹으로 증명한다.**

1. **`--self-check` (오프라인, Mac 과 VM 양쪽에서 실행 가능).** 실측한 `wg show wg0 dump`
   와 `/proc/net/dev` 출력 **형식**을 고정 표본으로 넣고 파서와 판정기를 합성 시계열로
   리플레이한다. 핵심 단언은 **「10.5초 단방향 정지를 잡는가」** 다 — 못 잡으면 self-check 가
   실패하고 task 가 실패한다. 임계값이 목적을 배반하지 못하게 하는 게이트다.
2. **임계값 주입 실관측 (읽기 전용).** 모든 임계값이 환경변수로 주입 가능하다.
   VM 에서 `WG_PROBE_STALL_SEC=1 WG_PROBE_TX_MIN_BYTES=1 ... --duration 45` 로
   **1회성 전경 프로세스**를 띄우면, 유휴 터널의 keepalive 만으로도 `rx_stall` 이 발화해
   판정→출력 경로 전체가 실측된다. 상시 유닛은 건드리지 않고, 데이터패스도 건드리지 않는다.
3. **무개입 증명.** 설치 전후로 `docker inspect -f '{{.State.StartedAt}}' gh-radar-relay` 가
   **같은 값**임을 확인한다 — relay 컨테이너가 재시작되지 않았다는 직접 증거다.
   `wg-quick@wg0` · `openconnect@kb` · `caddy` 활성 유지와 `ip route show default` = `dev ens4`
   도 함께 확인한다.

## 그 밖의 결정

- **journald 기록은 `logger -t` 가 아니라 `SyslogIdentifier=wg-probe` + stdout 이다.**
  기존 `kbvpn-watchdog`/`kbvpn-renew` 의 `logger -t` 는 10분/주 1회 도는 oneshot 이라
  fork 비용이 무의미하지만, 이건 1Hz 상시 데몬이다. 초당 프로세스 fork 금지(e2-micro 예산)
  규율을 지키면서 **`journalctl -t wg-probe` 조회 결과는 완전히 동일**하다.
  `ExecStart` 에 `python3 -u` 를 써서 파이프 버퍼링으로 줄이 늦게 나오는 것을 막는다.
- **ping 은 지속 프로세스 2개**(`ping -i 1 -O -n`)를 띄우고 출력을 스레드로 읽는다.
  초당 fork 0회. 프로세스가 죽으면 5초 백오프로 1회 재기동하고 `ping_restart` 를 남긴다.
  `ping` 이 아예 없으면 한 줄 남기고 wg 측정만으로 계속한다(수집기가 죽지 않는다).
- **권한.** `wg show` 는 netlink 라 CAP_NET_ADMIN 이 필요하다. `DynamicUser=yes` +
  `AmbientCapabilities` 경로는 **채택하지 않는다** — 이 호스트에서 실증하려면 살아 있는
  게이트웨이 위에서 실험해야 하고, 기동 실패의 대가가 하드닝 이득보다 크다. 대신
  `CapabilityBoundingSet=CAP_NET_ADMIN CAP_NET_RAW` 로 **두 능력만 남기고** 나머지를 전부
  떨어뜨리며, `ProtectSystem=strict`(파일시스템 전체 읽기 전용) · `NoNewPrivileges` ·
