# gh-radar → gh-trade 작업 요청 — 2026-11-25

> **계약 협의 단계(초안)다.** 사용자는 지금 gh-radar 쪽 화면 목업을 검토 중이고, 화면 확정 전에는 gh-radar 가 아무것도 커밋하지 않는다.
> gh-trade 쪽은 아래 「질문」 에 답(계약 결정 + 주문 성능 판정)을 먼저 주면 된다. 구현 착수 시점은 목업 확정 뒤 다시 알린다.

## 요청 내용

사용자 요청(2026-11-25): **09:00:30 'N' · 16:00 Q16 러쉬 주문의 뒤탐침**을

1. 발마다 **쏘는 시각을 자유롭게** 정하고(지금은 `(i+1)·step_us` 등간격만 된다), 같은 시각에 여러 발도 쏠 수 있게,
2. 탐침 시각을 **추가 · 삭제**할 수 있게,
3. 전체 탐침 시각을 한꺼번에 **±1 · 3 · 5 · 10µs** 옮길 수 있게(이건 웹 초안 도우미 — 서버는 결과 목록만 받는다),
4. 그러면서 **주문 성능(실조각 · 재전송)에 문제가 없는지** gh-trade 가 RT 루프 기준으로 판정해 달라.

지금 계약(Phase 47 · 인박스 261107-launch-tail-probe-op10)은 `(count 0..10, step_us 1..100)` 등차수열이라 1 · 2 를 표현할 수 없다.
gh-radar 제안 = **발마다의 오프셋 목록** — 「마지막 실조각 계획 시각 뒤 +µs」 축(지금과 같은 축) 그대로, 발 i 의 송신 지연을
`lastDelayUs + offsets_us[i]` 로 바꾸는 것. `count` = 목록 길이, 같은 값이 여러 번이면 그 시각에 연달아 쏜다.

## gh-trade 가 할 일 (초안 — 질문 답에 따라 바뀜)

- `.fbs`: op 10 이 오프셋 목록을 받는 칸 · 94 `LaunchTailProbe` 말미 append `offsets_us: [int]` → `sync-relay-schema.sh`.
  (선택지: op 10 이 **기존 `launch_offsets_us`(op 8 이 쓰는 칸)를 읽게** 하면 요청 쪽 새 칸이 필요 없다 — 어느 쪽이든 gh-trade 결정.)
- `LaunchPlan` 회차 사본 · `launch_plan.toml [tail_probe]` 에 발별 오프셋 저장(구 파일 `(count, step_us)` 은 `(i+1)·step` 으로 읽어 들임).
- `LaunchThread`: 콜드2 `PrepareTailProbes` 가 `int m_tailAtUs[kMaxTailProbes]` 에 복사, RT 루프 `TailProbeAtUs` 가 그 배열을 읽게(산술 → 배열 읽기).
- kind 17 round −2 `planned_us` = 마지막 실조각 + `offsets_us[i]`(같은 식).
- 86 문구: 오프셋 범위 밖 · 정렬 위반(또는 서버가 정렬) · 발 수 상한 초과.

## 배포 순서 제약

gh-radar 먼저 배포가 안전한가: 지금 계약처럼 **순서 무관**이 되게 하고 싶다 — 94 에 `offsets_us` 가 없으면(구 서버) 웹은 지금 등간격 편집 칸(또는
읽기 전용)으로 떨어지고, 신 서버는 구 relay 의 `(count, step_us)` op 10 도 계속 받아 주면 좋겠다(가능한지 질문 ⑤).

gh-trade 는 cloud-verify.sh 게이트 뒤 deploy.sh <broker> <env> 로 KB 120·121·교보 119 를 장 마감 뒤 배포한다.

## 확인 방법

- op 9 → 94 `tail_probes` 두 행에 `offsets_us` 목록(배포 직후 = 기존 count · step 을 펼친 값, 예 5발 · 10µs → `[10,20,30,40,50]`).
- op 10 으로 `[5,5,20,60]` 저장 → 86 code 0 「저장 — 다음 발사부터 적용」 → 94 plan_rev +1.
- 다음 발사 로그 `[Launch] 뒤탐침 무장 … offsets_us=5,5,20,60 …` · kind 17 round −2 `planned_us` 가 마지막 실조각 + 각 오프셋.

## 질문

① **오프셋 범위** — 최소 1µs(실조각보다 앞서지 않는다 불변식) · 최대는? gh-radar 제안 **1000µs**(지금 최악 10 × 100 = 1ms 정지 지연, Phase 47 D-08 에서
   수용한 값과 같은 축). 더 늘려도 되는가, 줄여야 하는가.
② **발 수 상한** — 그대로 **0..10**(`m_tail` · `m_tailPo` 고정 배열 · static_assert) 유지로 보면 되는가. 0 = 끔(빈 목록).
③ **같은 시각 여러 발** — 오프셋 중복(예 `[5,5,5]`)을 허용해 연달아 쏘는 것(스핀 없이 SendPrebuilt 연속)이 RT 루프 · 송신 게이트 · FEP 응답 줄에 문제 없는가.
④ **정렬** — 웹이 오름차순으로 정렬해 보낼 예정(16:00 계획 편집과 같은 규칙). 서버는 정렬 위반을 거부할지, 받아서 정렬할지.
⑤ **와이어 모양 · 하위 호환** — 새 칸 vs 기존 `launch_offsets_us` 재사용, 그리고 신 서버가 구 `(count, step_us)` op 10 을 계속 받아 줄 수 있는지.
⑥ **주문 성능 판정** — (a) 16:00: 뒤탐침이 실조각 버스트 **뒤** 루프라 실조각 송신 시각에는 영향이 없다고 보는데 맞는지, 오프셋 배열 읽기가 RT 규약(락 · 힙 · 로그 없음) 안인지.
   (b) 'N': 뒤탐침이 515 재전송(교보 ~23ms/건)보다 앞선 wire 라, 발 수 · 최대 오프셋이 지금 상한(10발 · 1ms) 안이면 재전송 지연이 지금과 같다고 보는데 맞는지.
   (c) 그 밖에 성능상 걸리는 것(정지 지연 · 다음 발사 준비 · 콜드3 수거 시간 등).

## 변경 2 — 절대 시각 「탐침」 (사용자 2026-11-25, gh-trade 답신 ① ~ ⑥ 뒤)

gh-trade 답신 ① ~ ⑥(한도 · 새 칸 · count = -1 구 서버 보호 · 비감소 거부 · ⑥(c) 경고)은 받았다. 그 뒤 사용자가 요구를 바꿨다:

- 이름 「뒤탐침」 → **「탐침」**.
- 축 = **정각 기준 절대 µs**(16:00:00.000000 · 09:00:30.000000 — op 8 `launch_offsets_us` 와 같은 축, 부호 있음). 「마지막 실조각 뒤 +µs」 아님.
- 웹은 − 를 기본으로 붙인다(대부분 정각 −Xµs) · `+` 를 붙이면 정각 뒤. 저장 때 비감소 정렬 · 중복 허용 · 0 ~ 10발 그대로.
- 결과: 탐침이 실조각 **앞 · 사이**에 올 수 있다 — 「실조각보다 앞서지 않는다」 불변식이 깨진다.

재판정 질문(세션 메시지와 같음):
① 범위 — 계획 한도와 같게 Q16 −3000 ~ +1000 · N −2000 ~ +2000 인가, 더 좁게인가.
② 실조각 앞 · 사이 탐침을 버스트에 끼울 때 실조각 송신 시각 영향(갈래별 · 'N' · 재확인 회차) · TX 배타 점유.
③ 서버가 거부할 것 vs 웹 경고 · 실조각과 같은 µs 일 때 순서.
④ ms 탐침(RunMsProbes, 15:59:59.200 경계 절대 시각)과의 겹침 · 충돌.
⑤ 이행 — 기존 (count, step) 을 그 회차 계획 마지막 실조각 + (i+1)·step 절대값으로 한 번 펼쳐 저장하는 안.
⑥ 와이어 — 새 칸 · count = -1 장치 그대로, 축 의미만 절대값.
