## RK-04 — gh-trade 에 돌려줄 내용 · 결정

### 1. 경계 표시 방식(gh-trade 질문의 답)

gh-radar 에는 `risk_*` 를 날짜 축으로 그리는 화면이 없다. 보고서 사건 카드 하나가 한 거래일의 잠김만 칩(「위험도 +3초 NN% · +10초 · +60초 · 깨짐/끝 3초 전」)으로 보여 주고, 칩 바로 아래 캡션이 **그 카드 날짜의 정의**를 적는다.

- 20261102 전: 「위험도 = 그 시점까지 누적 매도 ÷ 그 시점 대기 금액 · 100% 를 넘을 수 있다 · 2026.11.02 전 정의」 (`data-risk-def="krw"`)
- 20261102 부터: 「위험도 = 그 시점 상한가 거래량 ÷ 그 시점 대기 수량 · 100% 를 넘을 수 있다 · 2026.11.02 부터 정의」 (`data-risk-def="qty"`)

칩 숫자 서식(정수 %, 100% 초과 그대로, null → 「—」), 요소, 클래스, data-slot 은 경계 양쪽이 같고, 바뀌는 것은 캡션 문구와 `data-risk-def` 뿐이다. 새 레이아웃이나 title 툴팁은 넣지 않았다(캡션이 이미 칩 바로 아래 보이는 작은 라벨이고, title 은 모바일에서 안 보인다). 경계 날짜 정본은 `@gh-radar/shared` 의 `LIMITUP_RISK_QTY_FROM = "20261102"` 하나이고, 「2026.11.02」 라벨도 이 상수에서 만든다. webapp 에 날짜 리터럴은 없다. 판정은 `date >= LIMITUP_RISK_QTY_FROM`(YYYYMMDD 문자열 비교)이다.

### 3. 실시간 위험도 갈래표(T3 · `limitFeatureCells` 누적 행 셋째 칸)

갈래는 위에서부터 처음 맞는 것을 쓴다. 모든 갈래에서 tone 은 fg, narrow 는 없고, 반올림은 `roundPctHalfEven`(정수 짝수 반올림)이다. 매도 · 취소 두 칸과 `noLock` 식은 바뀌지 않았다.

| 갈래 | 조건 | 위험도 칸 | 언제 나오나 |
| ---- | ---- | -------- | ---------- |
| A | `limitVolQty` 키 없음 | 오늘 규칙 그대로: noLock → 「—」, qKrw 0 → 「위험도 —」, 그 밖 `lockSellKrw ÷ qKrw` | 구 relay(T3 배포 전) · kind 15 다리(`limitFeatureOfStrategyEvent`, 키를 싣지 않음) |
| B | 키 있음 ∧ limitVolQty 0 ∧ lockState ≠ 0 ∧ lockSellKrw > 0 | 옛 식 `lockSellKrw ÷ qKrw`(qKrw 0 → 「위험도 —」) | 새 relay + 구 gh-trade 서버(nd7 이전, 필드 부재 = 0) |
| C | 그 밖 | `qQty 0 ∨ (lock 0 ∧ limitVolQty 0)` → 「위험도 —」, 그 밖 `limitVolQty ÷ qQty` 정수 % | 새 relay + 새 서버(WinForms nd7 `noRisk` 와 같은 식). 잠기기 전(lock 0)에도 숫자를 낸다 |

**B 판별 근거.** 새 서버에서는 잠김 중 상한가 매도 주도 체결이 하나라도 있으면(lockSellKrw > 0) 그 매도가 상한가 거래량 카운터를 동결시키면서 셈에 들어간다. 카운터를 내리는 것은 상한가 미만 체결뿐인데, 잠김(매수1 = 상한가) 중에는 상한가 미만 체결이 날 수 없다. 그래서 lock 1 에서 「limitVolQty 0 ∧ lockSellKrw > 0」 은 필드를 싣지 않는 구 서버만 만든다. lock 2(깨진 뒤)는 새 서버에서도 상한가 미만 매도 뒤 0 이 될 수 있다. 하지만 그런 매도가 났다는 것은 그 순간 상한가 매수잔량이 없다는 뜻이라 qQty · qKrw 가 함께 0 이고, 두 식 모두 「위험도 —」 로 같다.

**받아들인 잔여.** 깨진 뒤 상한가 매수가 다시 쌓였는데 아직 상한가 체결이 없는 짧은 순간, 그리고 누적 역행으로 카운터가 다시 시작되는 이상 데이터에서는 새 서버인데도 옛 식 값이 보인다.

**배포 순서 안전성.** relay 와 webapp 중 어느 쪽이 먼저 나가도 화면이 0% 로 무너지지 않는다. webapp 이 먼저면 구 relay 는 키를 싣지 않으니 갈래 A(오늘과 같음)이고, relay 가 먼저면 옛 webapp 은 모르는 키를 무시한다.

**e2e 기대가 그대로인 근거.** `relay/tests/helpers/frames.ts` 의 기본 85 프레임은 `limitVolQty` 를 기록하지 않는다(0n = 구 서버 모양). lockSellKrw 는 6.0억 > 0 이고 lockState 는 1 또는 2 다. 그래서 webapp e2e(`trading-workbench.spec.ts` 「위험도 35%」 · lock 2 qKrw 2.1억 「위험도 286%」)는 갈래 B 로 가고 옛 식 값이 유지된다. Playwright 는 돌리지 않았고, 이 판단은 코드 경로와 shared 갈래 B 단위 테스트(35% · 286%)로 확인했다.

### 4. WinForms 와 의도적으로 다른 점 하나

WinForms `LimitChaserForm`(bac82294, 4041~4057행)은 limit_vol_qty 이전 서버를 옛 식으로 돌리지 않는다. 그래서 잠기기 전에는 「위험도 —」, 잠긴 뒤에는 「위험도 0%」 가 보인다(regression-checklist 8번). 웹은 사용자 안내(L-4 「구 서버는 옛 식」)를 따라 갈래 B 에서 옛 식 값을 보인다. 이 점만 다르고 나머지 갈래 C 는 WinForms 와 같다. gh-trade 서버가 nd7 로 배포되면 갈래 B 는 사실상 나오지 않는다.
