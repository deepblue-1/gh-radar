<objective>
relay 관찰자를 다중 업스트림으로 만든다. 교보 DMA 서버 kyobo127(`DMA_KYOBO_HOST`, 9100)에 관찰자 연결 하나를 KB 120 과 **동시에** 붙인다. 게이트웨이 키는 `KYOBO` 이고 비밀은 전용 `DMA_OBSERVER_SECRET_KYOBO` 다. 브라우저 `journal.state` · `/healthz` 기존 필드 · 사용자 세션(SessionManager, KB 단일)은 바뀌지 않는다.

Purpose: Phase 19 결정(19-CONTEXT :52 「관찰자는 게이트웨이당 1개, 교보 확장을 막지 않는 형태」 · :170 「relay 가 교보를 붙일 때 같은 설계로 확장한다」)의 실행이다. gh-trade Phase 22 가 교보 게이트웨이를 올렸다. radar-gw → 10.16.207.127:9100 경로는 2026-09-29 08:40 컨테이너 안에서 확인됐다. DB 는 이미 게이트웨이 키 PK · `p_gateway` advisory lock 구조라 마이그레이션이 필요 없다(계획 시점 확인: `dma_journal_cursor` PK gateway · `dma_account_access` PK (gateway, dma_user_id, account_no) · `dma_journal_apply`/`dma_journal_sync_access` 가 `hashtext('dma_journal:' || p_gateway)` lock).

Output: Task 1(gsd-executor · tracer)은 relay 코드와 테스트를, Task 2(gsd-executor)는 배포 · IAM 스크립트와 README 를 맡고 각자 커밋까지 한다. Task 3(**메인 세션 전용**)은 비밀 생성 → gh-trade 인계 → relay 배포 → 라이브 검증이다.

Tracer: Task 1 이 env → 설정 → 게이트웨이별 파이프라인 → Supabase RPC(`p_gateway`) → `/healthz` → 브라우저 푸시까지 한 경로를 끝단까지 잇는다. 실 relay 프로세스와 가짜 게이트웨이 2개로 증명한다(journal-boot M2). Task 2 는 그 경로를 운영 표면(배포 · IAM · 문서)으로 넓힌다.

계획 시점에 정한 설계 판단 (근거는 각 태스크 action):
- **거부 = 정지(D-13 · T-19-28)를 KYOBO 에도 그대로 둔다.** 롤아웃은 「비밀 생성 → gh-trade 가 kyobo127 에 observer.toml 배치 + 재시작 → relay 배포」 순서로 강제한다. 역순이면 KYOBO 가 rejected 로 굳는다. 복구는 relay 재시작 한 번이다(README 에 기록).
- **KYOBO 는 503 판정에 넣지 않는다.** 교보 터널은 약 4시간마다 재로그인하고, 데스크톱 SecuwaySSL 과 상호배제된다. 이 끊김이 KB relay-down 알림을 울리게 해서는 안 된다. 또 deploy-relay.sh 의 기동 확인이 `curl -sf` 라서, 장중 503 이면 KB 배포가 실패한다. 상태는 본문 `alerting` 으로 드러낸다. 한계(장중 KYOBO 끊김 알림 경로 없음)는 README 에 적는다.
- **브라우저 `journal.state` 는 KB 만 보낸다.** 프레임이 달라지지 않고 webapp 도 바꾸지 않는다. 가장 덜 침습적이다. 추가 변형 프레임을 보내면 기존 webapp 이 그것을 KB 「기록 지연」으로 그린다.
- **KYOBO 적용 행은 KYOBO 매핑으로 푸시한다.** REST 가시성 RPC 는 게이트웨이 구분 없이 dma_user_id 로 조인한다. 그래서 KYOBO 매핑이 DB 에 들어가는 순간 REST 복원에는 KYOBO 행이 뜬다. 푸시를 빼면 카드의 복원 행과 실시간 행이 어긋난다.
</objective>
