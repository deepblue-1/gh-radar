# 기획서(주문로그 · 잔량진행률) — gh-radar 쪽 함의 (2026-09-29)

## 1. 기획서의 대상은 KB 통보 저널이 아니라 「상따 전략 로그」 다

- 7종 로그(상한가노출 · 상한가진입 · 매수 주문 · 대기 · 체결 · 매도 주문 · 취소·거부)의 본문은 전부 gh-trade 서버 LimitChaser 가 아는 값이다: 조건 설정값/실측값 · 근거 틱 · 상한가 매수잔량 · 접수 +ms · 거래소별 누적거래량 · 체결예상 누적 · 오차 · 남은 거래량. 통보 저널(23필드)에는 하나도 없다.
- 따라서 오늘 오전에 대조한 notice_type × request_kind 템플릿은 「오늘 주문」 카드(통보 저널) 표시 개선에만 쓰이고, 기획서 로그와는 별개다. 기획서 로그는 서버가 문장(또는 구조화 레코드)을 만들고 gh-radar 는 표시·저장·조회만 한다.
- 스크린샷의 창은 WinForms 「상따전략」 창(탭 수동주문/정정취소/거래원/로그 · 미체결 밑 진행률)이다. 웹의 대응 표면은 작업대(`/trading/limit-chaser`) 하단 공용 패널의 「전략 로그」 탭과 카드 탭, 미체결 표다.

## 2. 현재 웹 전략 로그와의 거리

현재 `webapp/src/components/trading/strategy-log.tsx`: 60 에코 전이 + ServerMessage(54) 통지(source="LimitChaser" 사유 줄 포함)를 브라우저 메모리에만 쌓는다. 새로고침하면 사라진다(T-16-02, 사용자 결정 260911-w5h 로 고지 문구도 없음). 필터·새 로그 배지·창 분리·스크롤 고정·ms 시각 없음. `at` 는 HH:MM:SS 로컬.

기획서가 요구하는 것 중 웹에 없는 것:
| 요구 | 현재 | 필요한 변경 |
|---|---|---|
| ms 시각 | 초 단위, 클라 수신 시각 | 서버 발생 시각(ms) 을 레코드에 실어야 함 |
| 종목·거래소 필터 | 없음 | 레코드에 isin · exchange 구조화 필드 필요(54 는 isin 만, exchange 없음) |
| 구분(선매수/…) · 주문번호 · 이벤트 종류 | 문장 안에만 | 구조화 필드 필요(필터·저장·집계용) |
| 저장 · 비정상 종료 생존 · 나중에 조회 | 없음 | Supabase 적재 + 조회 경로. 관찰자 저널(5/79/80)과 같은 seq · epoch · 멱등 적용 모델을 재사용하는 것이 가장 싸다 |
| 새 로그 배지 카운트 · 창 분리 · 스크롤 고정 | 없음 | 웹 UI 작업(서버 무관) |
| 누적거래량 모든 줄 | 없음 | 레코드 필드 |

## 3. 와이어 제안 (gh-trade 와 합의할 것)

옵션 A — ServerMessage(54) 문장만: 서버가 7종을 54 source="LimitChaser" 문장으로 보내면 웹은 지금 코드로 바로 보인다. 그러나 필터·저장·ms·거래소가 안 되고, 문장 파싱 금지 규율(D-36 · T-17-33) 때문에 구조화 못 함. 임시 단계로만.

옵션 B(권장) — 구조화 레코드 + 저널 경로 재사용: fbs 에 `StrategyLogRecord` 테이블(seq · trade_date · gw_time_ms · exchange · isin · account_no · order_no("" 허용) · kind(선매수/추가매수/줄서기매수/호가매도/체결매도/"") · event(노출/진입/주문/대기/체결/매도/취소/거부) · cum_volume · text(서버 조립 문장 — 파싱 안 함) · 구조화 수치 몇 개(expected_cum · error · remaining_volume · accept_ms · 조건 설정/실측 등, 필요 최소)) 를 두고 관찰자 배치(80)에 함께 싣거나 별도 MsgType 으로 보낸다. relay 는 저널 기록기처럼 Supabase 에 멱등 적재 + 계좌 권한 사용자에게 푸시. 웹은 저장된 것을 조회(복원)하고 푸시로 이어 붙인다. 「비정상 종료돼도 남는다」 가 이 경로로 충족된다.
- 사용자 세션(51/54)과 달리 관찰자 경로는 계좌 전 범위를 기록하므로 다른 단말이 낸 상따 로그도 웹에서 보인다(오늘 주문과 같은 D-11 원칙).
- 문장은 서버 조립본 그대로 표시(파싱 금지), 필터·정렬은 구조화 필드로.

## 4. 2부 진행률 — 웹 표시 방식

- 계산 입력은 전부 서버 몫(기준 누적 · 내 앞 물량 · 경우 1/2 판정 · 단일가 구간 제외). 웹은 계산하지 않는다.
- 필요한 값: 대기 주문마다 `base_cum`(기준 누적) · `ahead_qty`(내 앞 물량) · `exchange` · `kind`. 현재 누적거래량은 웹이 이미 받는 시세 프레임(체결 `cum_volume`, 거래소별)에서 읽을 수 있으므로 `remaining = base + ahead − cum_now`, `progress = (cum_now − base) ÷ ahead` 를 웹에서 그리면 서버 푸시가 늘지 않는다. 단 웹이 그 종목·거래소 시세를 구독하지 않은 상태(마이페이지 등)면 현재 누적을 모르므로, 서버가 `remaining · progress` 를 같이 실어 주는 것이 표시 안전성이 높다. 둘 다 싣고 웹은 서버 값을 우선, 시세가 있으면 그 사이를 보간하는 것도 가능 — gh-trade 와 결정.
- 실을 자리: `UnfilledState` 말미 append(미체결 행 단위라 자연스럽고, 대기 주문 = 미체결 행 1:1) 또는 `LimitChaser` 에코의 런타임 필드. 미체결 행에 붙는 것이 「첫 체결·취소되면 줄 삭제」 와 맞물린다(미체결 삭제 = 진행률 삭제).
- 웹 표면: `account-panel.tsx` 미체결 목록 바로 밑 한 줄/대기주문(기본 모드 표·모바일 카드·임베드 표 3곳). 「줄서기매수 · 체결예상까지 12,000주 남음 [막대] 88%」. 목업 게이트(다크/라이트) 먼저.

## 5. 용어 정렬 필요

기획서 구분: 선매수 / 추가매수 / 줄서기매수 / 호가매도 / 체결매도 (추가매수→후매수, 줄서기매수→반등매수 로 바뀔 수 있음). Phase 24 웹 UI 용어: 선매수 / 추가매수 / 후매수. 「추가매수→후매수」 로 바뀌면 웹의 현재 「추가매수」(최소~최대 잔량 조건) 와 「후매수」(반등 매수) 가 어느 쪽인지 서버·웹·기획서 셋이 같은 표를 써야 한다. 로그 kind 값은 코드(enum)로 보내고 표시 단어는 웹이 매핑하는 것이 안전하다.

## 5b. 사용자 결정 (2026-09-29)

- 1부 주문로그는 두 표면: (a) 오늘 주문 카드 — 주문 행 펼침에 이벤트 시간순, (b) 작업대에 별도 「주문로그」 탭 신설 — 시간순 평면 목록 + 종목·거래소 필터. 기존 「전략 로그」 탭은 설정 이력(내가 세팅을 어떻게 했나)으로 그대로 분리 유지, 통합하지 않는다.
- 목업은 gh-radar 웹 목업과 gh-trade WinForms 목업을 나란히 본다(둘 다 사용자 화면에 열어 둠).
- **진행률 채택안 = B**(대기 행 아래 2줄째 「줄서기매수 · 체결예상까지 N주 남음 [막대] P%」), 웹·WinForms 공통. 웹은 데스크톱 표·임베드 표에 보조행, 모바일 카드는 r3 줄. 막대 90% 이상 up 색.

## 6. gh-radar 작업 후보 (기획서 확정 뒤 GSD phase)

1. 전략 로그 표면 개편: 저장·복원 조회 · 종목/거래소 필터 · 새 로그 배지 · 창 분리(새 창 라우트) · 스크롤 고정 · ms 시각.
2. relay: 새 레코드 수신·적재·푸시(옵션 B 채택 시). Supabase 테이블 + RPC(서비스롤 전용, 명시 REVOKE).
3. 미체결 밑 진행률 줄(3 표면) + 목업 게이트.
4. 오늘 주문 카드 개선 3건(방향 미상 「주문」 · 접수불명 상태 · R 방향 참고)은 별건으로 유지.
