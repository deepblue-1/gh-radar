## ② 정정 — 터널 IP 는 계정 고정이 아니라 풀 할당

plan 과 CONTEXT 는 *"Mac 실측이 3회 모두 `10.41.1.124` 였으므로 계정 고정 추정"* 이라고 기록했으나 **이번 실측으로 반증됐다.**

| 관측 시점 | Mac (`utun4`) | VM (`tun0`) |
|-----------|---------------|-------------|
| 선검증 직전 | `10.41.1.126` | (미연결) |
| 선검증 중 (동시) | `10.41.1.126` | `10.41.1.124` |

- Mac 이 과거 3회 `.124` 를 받았던 것은 **그때 그 주소가 풀에서 비어 있었기 때문**이다. 이번에 Mac 은 `.126` 을 받았고, 오히려 **VM 이 `.124` 를 받았다.**
- 따라서 **터널 IP 는 세션마다 달라진다.**

> ⚠️ **후속 plan 주의:** 터널 IP 를 고정값(`10.41.1.124` 등)으로 하드코딩하거나 allow-list 에 넣지 말 것.
> 필요하면 연결 후 `ip -4 addr show tun0` 로 **런타임에 조회**해야 한다.
> 반대로 게이트웨이 주소 `10.41.1.120` 은 서버측 고정값이므로 상수로 다뤄도 된다.

## ⑤ 라우팅 diff (핵심 증거)

**연결 전 (14:27:49Z) — 4행**

```

10.10.0.1 dev ens4 proto dhcp scope link src 10.10.0.5 metric 100
169.254.169.254 via 10.10.0.1 dev ens4 proto dhcp src 10.10.0.5 metric 100

```

**연결 후 (14:29:03Z) — 7행. 추가된 3행만 아래에 표시**

```
+ 10.41.0.0/16 dev tun0 scope link
+ 10.41.1.0/24 dev tun0 scope link
+ <VPN서버IP> via 10.10.0.1 dev ens4 src 10.10.0.5 metric 100
```

- **`default` 행은 변하지 않았다** — `CISCO_SPLIT_INC` 래퍼가 서버 푸시 라우트를 덮어쓰는 데 성공했다.
- 터널로 가는 것은 **KB 대역(`10.41.0.0/16`)뿐**이다.
- 세 번째 추가 행은 VPN 서버 자신에 대한 호스트 경로이며 `ens4` 를 통한다(정상 — 터널 밖으로 나가야 한다). 주소는 `/etc/kbvpn.env` 에만 있으므로 여기서는 마스킹한다.

**정지 후** — 기준선 4행과 **완전히 동일**하게 복원. `tun0` 소멸, 공인 IP `34.22.79.103` 유지.

## 안전장치 운용 (T-15-11)

기존 `kbvpn-route-guard` 는 "기본 경로가 `tun*` 로 넘어간 경우"만 잡고, **기본 경로는 유지되면서 GCP 관리 경로만 죽는 부분 탈취는 못 잡는다.** 그래서 무조건 정지 데드맨을 하나 더 걸고 시작했다.

| 타이머 | 성격 | 예약 | 결과 |
|--------|------|------|------|
| `kbvpn-route-guard.timer` | 조건부 (기본 경로 탈취 시 VPN 중지) | 연결 직전 180초 | 미발화 (검증이 먼저 끝나 해제) |
| `kbvpn-deadman.timer` | **무조건** 10분 뒤 `systemctl stop 'openconnect@*'` | 연결 직전 600초 | 미발화 — 검증 정상 종료 후 **수동 해제 완료** |

- 연결 명령과 관측 명령을 **별도 SSH 호출로 분리**했다. 라우팅이 탈취되면 그 SSH 호출 자체가 끊기므로, 안전장치가 먼저 예약돼 있어야 복구된다.
- 검증 종료 후 `systemctl list-timers 'kbvpn-*' --all` = **0 timers** (둘 다 해제 확인).

## 비밀 취급 (T-15-26)

- `/run/kbvpn.cred` 는 연결 중에만 존재하고, `systemctl stop` 후 `ExecStopPost` 가 **삭제한 것을 실증**했다 (`ls: cannot access '/run/kbvpn.cred'`).
- 접속 비밀 값·계정 ID·서버 주소·인증서 핀은 이 문서·커밋·대화 어디에도 기록하지 않았다.

## 부수 관측

- openconnect 로그에 `Server certificate verify failed: signer not found` 가 나오지만 **정상이다.** KB VPN 서버 인증서가 공인 CA 체인이 아니어서, `--servercert pin-sha256:...` 핀 검증으로 대체하는 설계이기 때문이다. 핀이 일치했기에 연결이 진행됐다.
- 서버가 통보한 **세션 인증 만료: 2026-09-19** (약 14일). 상시 운용 시 재인증 주기로 고려해야 한다.
- 연결 방식: CSTP + DTLS 동시 성립 (DPD 30 / Keepalive 20).
