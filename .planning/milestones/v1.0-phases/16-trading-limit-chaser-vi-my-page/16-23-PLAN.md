**CR-01 + WR-08** 을 닫는다. 「사용자가 고른 계좌」와 「마지막으로 프레임이 온 계좌」를 혼동하는 소비자 2곳을 고치고, **그 혼동이 가능한 계약 자체를 없앤다.**

지금 상태:
- `stock-orderbook-section.tsx:452` 가 `AccountPanel` 에 `selectedAccountNo={selectedAccountNo}`(사용자 선택)와 `account={account}`(전역 「마지막 수신 계좌」)를 **서로 무관한 두 출처**에서 넘긴다. 같은 파일 L138~141 의 주석이 스스로 「그 어긋남이 곧 엉뚱한 계좌의 주문을 취소하는 사고다」라고 적어 둔 바로 그 어긋남이다. 실패 경로: 계좌 A 선택 → 계좌 B 체결로 67 델타 도착 → 머리는 A, 행은 B → `✕ 취소` 가 `accountNo: A` + `orgOrderNo: B의 주문번호` 로 나간다 → relay 화이트리스트는 통과한다(A 는 그 사용자의 계좌다) → **A 계좌에서 엉뚱한 주문이 취소된다.** 잔고 탭 평가손익과 매도가능수량(`:254~256`)도 같은 이유로 다른 계좌 값이다.
- `app-sidebar.tsx:246~260` 의 ISIN→종목명 역매핑만 `account` 하나를 본다. 같은 역할의 다른 두 구현(`limit-chaser-client.tsx:865~880`, `strategy-status-card.tsx:97~114`)은 `accountStates` 전체를 훑는다 — **세 사본의 동작이 서로 다르다.** 계좌 2개 이상에서 사이드바 3단 목록만 `KR7005930003` 같은 ISIN 원문으로 그려지고, 프레임이 올 때마다 표시가 왔다 갔다 한다.

**근본 해결:** 두 소비자를 `accountStates` 로 옮기는 데 그치지 않고, `RelayConnectionState`/`RelaySocketState` 에서 **`account` 필드를 제거**한다. 실측상 그 필드의 소비자는 위 두 곳뿐이므로, 고친 뒤에는 남는 소비자가 0이다. 노출된 채로 두면 다음 소비자가 같은 실수를 반복한다.

Purpose: 계좌 경계를 「소비자가 올바른 필드를 고르는 규율」이 아니라 **타입 계약**으로 만든다.
Output: `account` 제거 · `accountStates` 를 구독 계약에 노출 · 두 소비자 수정 · `lib/isin-labels.ts` 공용 훅 · 회귀 테스트.
