전송은 반드시 `this.#send(conn, ...)`(이 연결) 또는 `#deliver(userId, ...)`(그 사용자 전 연결) 기존 경로만 쓴다 — 새 전송 함수를 만들지 않는다(T-16-02). 여기서는 **방금 인증한 그 연결에만** 내리는 것이 맞으므로 `#send(conn, …)` 이다(계좌 스냅샷과 동일).

① **`keyOf` 이동**: `#onAuthedMessage` 의 `const key = keyOf(msg.isin, msg.ex)` 를 `sub`/`unsub` 분기 **안쪽**으로 옮긴다. 이동만 하는 커밋 단위로 다루고, 옮긴 이유를 한 줄 주석으로 남긴다(Pitfall 14).

② **`FanoutSessions` 인터페이스 확장**: `get(userId): DmaSession | undefined` 를 추가한다(`SessionManager` 에 이미 존재). 전략 전송이 `session.send()` 와 `session.allowedAccounts` 를 필요로 한다. `WsFanoutDeps` 는 그대로 두되 타입만 넓힌다.

③ **전략 분기 4종** — `conn.unauthorized` 가드 뒤, sub/unsub 앞. 각 분기는 아래 **공통 3단계**를 거친다(순서 고정, `order-api.ts` ①②③ 를 그대로 이식):
   1. 세션 확인: `sessions.get(userId)` 가 없거나 `!isReady` → `{t:"state", s:<현재상태>}` 또는 서버메시지 성격의 거부 프레임을 되돌리고 **로그를 남긴다**(조용한 무시 금지). 여기서 대신 로그인하지 않는다.
   2. **계좌 화이트리스트 대조**: `lc.set` 의 `cfg.accountNo`, `vi.set` 의 `accountNo` 가 `session.allowedAccounts.some(a => a.accountNo === …)` 를 통과해야 한다. 통과 못 하면 `logger.error` + 거부 프레임(계좌번호는 `maskAccountNo` 로 마스킹해 로그). **상태 프레임의 계좌 사본이나 요청 바디를 근거로 삼지 않는다** — 원천은 `session.allowedAccounts` 뿐이다(T-16-01). `vi.confirm`/`strategies.disable` 은 계좌 필드가 없으므로 이 단계를 건너뛴다.
   3. 조립·송신: `buildSetLimitChaserReq(cfg)` / `buildSetVITriggerReq(...)` / `buildConfirmVIOrderReq(...)` / `buildDisableStrategiesReq(key ?? "")` → `session.send(payload)`. `false` 면(송신 실패) 사유를 로그하고 거부 프레임을 되돌린다. `OrderBuildError` 등 조립 예외도 같은 경로로 잡아 사용자에게 알린다 — **삼키지 않는다**(PC-7).

   **응답을 기다리지 않는다**: 전략 메시지의 결과는 60/61/64/65 에코로 오며 Hub → `#deliver(userId)` 로 전 연결에 팬아웃된다(D-11/D-12). 요청/응답 상관은 주문(16-08)만 한다.

④ **인바운드 rate-limit**: 전략·주문 메시지는 server 의 `apiRateLimiter` 를 우회하는 새 경로다. 연결당 **초당 10건**(재량 상한, 상수로 노출) 토큰 버킷을 `#onAuthedMessage` 초입에 두고 초과 시 프레임을 드롭 + `logger.warn` 1회(연속 경고 폭주 방지). `sub`/`unsub` 도 같은 버킷을 쓴다.
