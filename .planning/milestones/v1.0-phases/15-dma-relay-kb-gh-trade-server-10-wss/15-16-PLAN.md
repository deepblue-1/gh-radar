바디 zod 스키마: `{ userId: uuid, orderRowId: uuid, isin: 12자, exchange: "KRX"|"NXT", market: "K"|"Q", side: "B"|"S", orderType: "N"|"C", orgOrderNo?: string, qty: int>0, price: int>0, accountNo: string }`. **금액·수량 한도는 두지 않는다**(D-20 — 형식 검사만). 검증 실패 → 400 `{error:{code:"VALIDATION_FAILED", ...}}`.

처리 순서:
1. `sessionManager.get(userId)` — 세션이 없거나 `ready` 가 아니면 **409 `SESSION_NOT_READY`**(D-15). lazy 로그인을 하지 않는다.
2. **`accountNo` 가 그 세션의 계좌 목록에 있는지 대조** — 없으면 **403 `ACCOUNT_NOT_ALLOWED`**(D-20, T-15-01 IDOR 방어). 이 대조가 relay 쪽 최후 방어선이다.
3. `orderType === "C"` 면 `orgOrderNo` 필수(없으면 400) + `qty > 0` 필수. **취소수량 0 은 400 으로 즉시 거부**(Pitfall 7).
4. `buildDirectOrderReq` 로 조립 후 세션으로 송신. 동시에 **`orderRowId`/`accountNo`/`isin` 기준 pending 맵**에 5초 타이머와 함께 등록한다.
5. 첫 `OrderResp(51)` 수신 시 pending 을 해소하고 `{orderNo, resultCode, message, status: "accepted"|"rejected"}` 를 HTTP 응답한다. 5초 내 미수신 → **`504` 가 아니라 `{code:"ORDER_TIMEOUT"}`** 형태로 응답하고 `dma_orders.status='timeout'` 을 큐에 넣는다. **"실패"로 단정하지 않는다**(Pitfall 9) — "보냈는지 안 보냈는지 모른다"가 진실이다.
6. 이후 도착하는 `OrderResp`(체결 `E` / 취소확인 `C`)·`TradeExecution(53)`·`OrderConfirm(52)` 은 **그 주문자(userId) wss 소켓 집합에만** `{t:"order", ...}` 로 푸시하고 `orderStore.enqueueUpdate(...)` 로 DB 갱신을 큐잉한다. **전역 브로드캐스트 경로를 만들지 않는다.**
