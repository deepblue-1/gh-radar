**RelayProvider — 주문 잠금 (R3-WR-02 · 사용자 결정 1 · 2 · R3-IN-02).**
- 상태는 `useReducer` 하나다: 키 → `{ inFlight: number; resultUnknown: boolean }`. 키는 `strategyKey(isin, accountNo, exchange)`(`@/lib/limit-chaser` — 새 키 형식을 만들지 않는다). 액션은 셋 — 시작(진행 중 +1) · 정산(진행 중 −1, 그리고 timeout 이면 결과 모름 true — **한 액션**이라 두 상태 사이에 풀린 틈이 없다) · 초기화. 두 값이 모두 비면 키를 지운다.
- 파생값 `orderLocks: ReadonlyMap<string, OrderLockKind>`(`export type OrderLockKind = "in-flight" | "result-unknown"`) — 결과 모름이면 `"result-unknown"`(우선), 아니면 진행 중 > 0 이면 `"in-flight"`. `useMemo` 로 상태가 바뀔 때만 새 인스턴스를 만든다.
- 번역기 `sendOrder`: `buildOrderFrame` 을 통과해 **실제로 보내는** 요청이고 `req.kind` 가 `"new"` 또는 `"modify"` 일 때만 보내기 직전 시작을 반영하고, `sendOrderFrame` 결과를 받으면 정산을 반영한 **뒤에** 그 결과를 호출자에게 돌려준다(호출자의 `await` 뒤 렌더가 이미 새 잠금을 본다). `"cancel"` 은 어느 쪽에도 등록하지 않는다 — 취소 재시도는 무해하고 relay 가 같은 원주문의 중복 취소 대기를 거부한다(T-16-10 · 사용자 결정 2). 형식 오류로 보내지 않은 요청은 등록하지 않는다.
- 해제는 둘뿐이다: `useAuth().user?.id` 가 바뀌는 커밋의 효과에서 세대 ref 를 올리고 초기화한다(로그아웃 · 다른 사용자). 요청 시작 때 세대를 잡아 두고, 결과가 왔을 때 세대가 바뀌었으면 정산을 반영하지 않는다 — 로그아웃 순간 단절 정산(`abandonPendingOrders` 의 timeout)이 다음 사용자의 잠금이 되지 않게(T-18-141). 새로고침은 Provider 재생성으로 자연히 비운다. 해제 버튼 · 타이머 · 에코 해제는 두지 않는다. 잠금은 메모리 상태이며 브라우저 저장소에 쓰지 않는다.
