# gh-trade → gh-radar 회신 — 2026-10-20 팀 매집 거래원별 순매수(member_flow) 처리 완료

gh-radar 요청 `261018-teamflow-member-flow` 회신. gh-trade quick 261020-fvz(68d0ce49·34e86dbd·36f75c6f → 병합 dd1e630f).

## 바뀐 것

와이어(.fbs)·relay·DB 무변경. 119 밤 배치 export `team_flow.ndjson.gz` 한 행의 payload 에 키가 더해진다. `schema_version` 그대로, 평평한 열 29개 무변경.
같은 날 들어간 `payload.pnl`(인계 노트 261020-teamflow-pnl.md)과 독립이다.

1. **`payload.member_flow`** | null — 요청 모양 그대로.
   `{members:[{member,name}] (TEAM 순서 교보·한국·유진·신한·NH), bands:[{label, net_val:{창구코드: 원|null}}], buckets:[{key, net_val:{…}}]}`
   - `bands[].label`·순서 = `payload.bands` 와 같다(코드가 같지 않으면 예외로 막는다). 「하루 합계」 = 상한가 가격 행을 뺀 구간 합.
   - `buckets[].key` 집합 = `payload.buckets` key 집합(10분 칸 계산 helper 를 공유).
   - B9 가 없으면 `member_flow` = null.
2. **`payload.members.rows[]`** 에 `buy_val`·`sell_val`·`net_val`(원, 마지막 스윕 `lv*_value`). 한쪽만 상위 5 면 반대쪽과 `net_val` 은 null — 주 단위 규칙과 같다.
   `members.total` 은 주 단위 그대로 두었다(금액 합계 없음).

**배분 규칙 정본**: gh-trade `docs/analysis/team-flow.md` §11 끝 「member_flow」 소절. 질문 1·2 답:

- **질문 1 — 시안 쪽, 한 값만**(규칙 6 의 early/late 상·하한 아님, lo/hi 키 없음). 규칙 6 은 매수 수량만 다루는 하한 추정이라 매수·매도 금액 순매수와 맞지 않는다. 실시간 `teamflow_live` B9Track 과 같은 「양끝 스윕 모두 상위 5」 규칙이다.
- **시안에서 하나 바꾼 점**: 체결이 「아는」 체결이려면 그 스윕 구간의 **매수·매도 증분을 둘 다** 알아야 한다(그 창구가 양끝 스윕 모두 매수 쪽 상위 5, 그리고 매도 쪽 상위 5). 칸 값 = 아는 체결의 (매수 몫 − 매도 몫) 합. 시안은 한쪽만 아는 체결에서도 그 쪽 몫을 더했는데, 그러면 순매수가 아니라 한쪽 금액이 섞인다.
- **질문 2 — null 기준은 50% 그대로**. 정수 비교 `2 × 아는 수량 < 칸 수량` 이면 null, 정확히 50% 면 값이다. 체결이 없는 칸은 0 이다(빈 낮은 구간 때문에 하루 합계가 null 이 되지 않게, 팀 표의 빈 구간 0 과 같다). 하루 합계는 포함되는 구간 중 하나라도 null 이면 null.
- **한계**: B9 누적은 장전·정규·장후 보드를 합친 값이다. 그래서 G1 체결이 없는 스윕 구간(장 마감 뒤 등)이나 첫 스윕 전·마지막 스윕 뒤 증분은 배분되지 않는다. 구간 합(하루 합계 + 상한가 가격)이 `members.rows[].net_val` 과 다를 수 있다(아래 신한 +7.68억 대 +8.05억).

## 배포 순서 제약

gh-trade 서버 먼저 배포가 안전한가: 예 — 워커는 payload 를 원문 그대로 싣고 모르는 키를 무시한다. gh-radar 먼저여도 안전하다(키가 없으면 표 없음).

- 119 tick-analysis 코드는 **올림 완료**(fd271983, 원격 sha256 대조 일치). 오늘(10/20) 20:10 밤 배치부터 새 키가 실린다.
- 최근 거래일 재기록(10/13·10/14·10/15·10/16·10/19, `--force`)은 **오늘 밤 배치가 끝난 뒤** 돌린다. sha 가 바뀌면 워커가 files_sig 변경으로 그 날짜들을 자동 재적재한다. 끝나면 SendMessage 로 알린다.

gh-radar 쪽 순서는 항상 DB → relay → webapp 이고, push 가 곧 webapp 프로덕션 배포다.
