## 바뀐 것

아직 와이어 무변경(요청 단계). 사용자 결정(2026-10-27):

- **16:00 예약 발사의 보정치(학습)를 없앤다.** 발사 시각은 사람이 어드민에서 정한다.
- **어드민에서 서버별 · 발사별 · 시장별로 「조각 수 + 조각마다 발사 시각」 을 정한다.** 예: KB120 · 16:00 · 코스닥 = 3조각 `−350µs, −345µs, −325µs`.
- 적용 대상 발사 둘: **16:00 Q16 예약 발사**와 **09:00:30 NXT 개장차익(N)**. 09:00:27 KRX(A)는 지금처럼 명목 시각(대상 아님).

- 채널은 기존 **admin 관찰자(role 2) 연결 · `AdminCommandReq`(44) 새 op** 로 갈 예정이다(op 6 한도 · op 7 비용률과 같은 길). 응답 86 · 조회 응답 모양은 정식 노트에서.

## gh-radar 가 할 일

1. **목업** — 어드민에 「발사 계획」 편집 화면. 서버 × 발사(16:00 · 09:00:30) × 시장(코스피 · 코스닥) 칸마다 조각 수와 조각별 시각(µs)을 고치고 저장한다. 같은 화면이나 옆에 **발사 경계 지도(지금 만드는 것)** 로 바로 가는 길이 있으면 좋다 — 지도를 보고 시각을 정하는 흐름이다. 마지막 변경 시각 · 변경자 표시 여부는 목업에서 사용자와 정한다.
2. **사용자 승인** — 목업을 사용자에게 보여 주고 승인을 받는다.
3. **구현은 정식 인계 노트 뒤** — op 번호 · 필드 · 거부 code · 조회 응답이 정식 노트에 온다. relay 는 기존 op 6/7 처럼 admin 명령 중계만 늘면 된다.
4. **261027-launch-gate-contract 와의 관계** — 같은 gh-trade 페이즈에서 함께 처리한다(kind 17 · 18 발사 기록 + 이 발사 계획). **kind 18 의 Q16 학습값 칸(`correction_before/after_us` · `step_us` · `last_dir` · `bracketed` · `same_dir_run` · `reject_span_us` · `jump`)은 보정이 없어지므로 빠지거나 뜻이 바뀐다.** `next_offset_us` 는 「그 시점의 발사 계획 첫 조각 시각」 이 된다. 지금 만드는 `launch_heads` 표 · 해석 함수 자리는 그 칸들을 확정 전 상태로 두어 달라. (가) 백필 ndjson 은 따로 지금 뽑아서 보낸다.

## 배포 순서 제약

gh-trade 서버 먼저 배포가 안전한가: 예 — 새 op 를 모르는 relay/웹은 그 op 를 보내지 않을 뿐이고, 서버는 저장된 계획(없으면 초깃값)으로 발사한다. 반대로 웹이 먼저 나가 새 op 를 보내면 구 서버는 code 1 「알 수 없는 명령입니다」 로 거부한다(op 6/7 과 같은 가름).

gh-radar 쪽 순서는 항상 DB → relay → webapp 이고, push 가 곧 webapp 프로덕션 배포다.
