### ② 조회 계약 — 그대로 수용 + 차이 2건

인박스 ② 표를 **그대로 받는다** — 인자 5토큰 · stdout = pcap-ns 레코드 헤더 `<IIII>` 16B + 페이로드 반복의 zstd 프레임(전역 헤더 없음, recv 순) · stderr 끝 줄 JSON · 종료코드 0/75/64(그 밖 1) · 압축 16MB · 동시 1 · 여섯 태그(A3·B6·R8·B9·C3·A0)·ISIN 오프셋(A3/B6 17 · R8 15 · B9/C3 5 · A0 27)·길이 무검사 · 코어 0·nice 19·ionice idle · radar-gw 쪽 `tickpull`.

**차이 2건**(README 「gh-radar 제안과의 차이」 원문):

1. **stderr JSON 에 `compressed_files_skipped`(정수) 추가** — 20:00 보류 창이 끝나면 기록기가 `.pcap` 을 `.pcap.zst` 로 바꾼다(`zstd --rm`). 그 파일의 엔트리는 원본이 없어 건너뛰고, 건너뛴 파일 수를 이 필드로 센다. zst 를 풀어 다시 훑지 않는다 — 그날 밤부터는 GCS 변환 몫이다.
2. **0건 응답도 stdout 에 빈 zstd 프레임 1개** — stdout 은 항상 정확히 1프레임이다(이어붙이기 불변식: 응답 N 개 = 프레임 N 개). `has_more` 로 끊은 응답도 1프레임이다.

끝 줄 JSON 예(공백 없음, ns 세 값은 문자열):

```
{"fmt":"pcapns-rec/1","records":3,"first_recv_ns":"1762045201000000100","last_recv_ns":"1762045206000000600","has_more":false,"next_from_ns":"0","compressed_files_skipped":0}
```

참고(차이는 아니고 정밀화):

- 16MB 는 **엄격 상한**이다 — 제안의 「넘으면 그 자리에서 끊는다」 를 「넘기 전에 끊는다」 로 바꿨다(압축 누적이 16MB − 256KB 에 닿은 뒤 레코드 경계에서 끊는다 — 압축기 대기분 ≤ 1블록이라 닫힌 프레임이 16MB 를 넘지 않는다).
- `next_from_ns` = **보내지 않은 첫 레코드의 recv_ns**(다음 호출 `from_ns`, 포함 커서). 같은 recv_ns 묶음 사이에서는 끊지 않는다(가르면 포함 커서가 묶음을 중복 전송).
- 범위는 **from 포함 · to 배타** · `to_ns=0` = 지금까지.
- 「오늘」 = 119 호스트 로컬(KST) 날짜. 다른 날짜는 64. 00:00 ~ 그날 첫 파일 사이는 0건 exit 0(빈 프레임 1개).

**2) ① 의 20:30 경계** — 맞다, 유지한다. 기록기는 종료 시각이 없다(24시간 가동). 정시 압축 보류 창 07:00~20:00 이 끝나는 20:00 에 대기 파일을 하나씩 압축하기 시작하고, 20시 파일은 **21:00 회전** 뒤 압축된다. 완결은 `.pcap` 짝 소멸로 판정하므로 **21:30 회차**가 08~20시 파일을 전부 잡는다(20:30 은 보조 장치). 21시 파일(야간 배치, 수십 KB)은 다음 회차.

**3) 16MB · 동시 1** — 그대로 받는다(동시 2 는 열지 않는다 — flock 하나). 근거: 11/2 기록기 `[stats]` KRX 9.6억 pkts drops 0 · NXT 2.7억 drops 0, 색인 쓰기 약 1.1GB/일 순차 append, 조회 1회 ≈ 원시 수십 MB `pread` + zstd −3, 코어 0·nice 19·ionice idle. **배포 다음 거래일 장중 drops 0 유지와 응답 지연을 실측해 2차 회신**한다. 나쁘면 상한을 8MB 로 내리는 길을 열어 둔다 — 지금 상한은 상수라 그때는 `--max-bytes` 옵션을 새로 두고 이 인박스로 먼저 알린다.

## gh-radar 가 할 일

- 생성물 재동기화 불필요(와이어 무변경) · relay 파서·DB 마이그레이션·웹 변경 없음(이 노트 기준).
- **tickgw**: 차이 2건 반영 — stderr 끝 줄의 `compressed_files_skipped` 읽기(값 > 0 이면 그 시간대가 이미 압축됨 → 「당일 자료 준비 중」 카드로 넘어가도 된다) · 0건 응답의 빈 zstd 프레임 1개 수용 · 16MB 엄격 상한 · 포함 커서 `next_from_ns`.
- **radar-gw 측 `tickpull` 시스템 사용자·ed25519 키(주석 `radar-gw-tickpull`, 없을 때만 생성)는 gh-radar(tickgw 설치기) 몫** — gh-trade `tickarc`(`server/tools/archive/install.sh` ③④)와 같은 결. 119 호스트키 지문 대조도 설치기에서.
- 공개키 본문을 요청 노트(261102-tick-viewer-contract) **추기로 1회** 전달 → 사용자가 119 에 등록 → gh-trade 2차 회신 뒤 tickgw 를 **20:00 KST 이후에만** 켠다.
- 「거래소순」·런 닫기 규칙에 R8·A7(KRX)·E1·A6(NXT) 칸과 NXT G3 보드(B6 없음) 반영.
- B2·B0(·A7·E1) 포함 여부 결정.

## 배포 순서 제약

gh-trade 서버 먼저 배포가 안전한가: **예** — 과거 경로(GCS 변환)는 119 무관이고, 당일 경로는 119 인덱서 배포(평일 20:00 이후, 사용자 지시) → 키 등록 → 2차 회신 뒤 tickgw 순이다. relay·stock-dma·클라 무변경 — stock-dma 재기동 없음.

gh-radar 쪽 순서는 항상 DB → relay → webapp 이고, push 가 곧 webapp 프로덕션 배포다.

- radar-gw tick-archive 재설치(21:30 타이머)는 119 인덱서 배포와 같은 날 밤 — 2차 회신에 통보한다.
- tickgw 는 2차 회신(가동 통보)을 받기 전까지 켜지 않는다.

## 확인 방법

2차 회신에 실을 것(gh-trade 실측):

- 119 `systemctl show -p CPUAffinity,Nice,IOSchedulingClass tick-indexer` — 코어 0 · 19 · idle.
- 배포 다음 거래일 장중 기록기 `[stats] drops=0` 유지.
- 하루치 질의(`<isin> KRX <오늘> <08:00 KST epoch ns> 0`) 응답 크기·지연, 16MB 근처 종목의 `has_more` → `next_from_ns` 이어받기, 동시 2회 호출 중 하나가 75.
- radar-gw `systemctl list-timers tick-archive.timer` NEXT 21:30 KST, 다음 날 `journalctl -u tick-archive` 요약 줄 `[tick-archive] uploaded=…` 에 D 의 08~20시 파일.

gh-radar 쪽 확인(요청 노트 「확인 방법」 그대로):

- ①: radar-gw `journalctl -u tick-archive` 의 D 회차(이제 21:30) 요약 줄에 D 의 08~20시 파일이 잡히고, `gcloud storage ls gs://gh-trade-tick-archive/raw/krx/<D>/` · `raw/nxt/<D>/` 에 그날 밤 객체가 있다.
- ②: 인덱서 배포 + 키 등록 뒤 gh-radar 가 radar-gw 에서 `ssh … <isin> KRX <오늘 YYYYMMDD> <08:00 KST epoch ns> 0` 로 하루치를 실측 — 응답 크기·지연·16MB 초과 시 `has_more` → `next_from_ns` 이어받기·종료코드 75 동작. 결과는 gh-radar 37-17 SUMMARY 에, 차이는 인박스로.
